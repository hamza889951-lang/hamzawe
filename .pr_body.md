## 5. Actual event object structure — FINAL (live-verified contract)

Full live evidence chain (M0 TEST project, Cloud-log captures):
1. **METADATA capture:** `e = { clientPlatform, hostApp, commonEventObject:{hostApp,platform}, calendar:{id, calendarId, organizer, capabilities} }` — no `selectedEvent`/`calendarEventObject` in this runtime.
2. **READ capture (build tag live-verified):** same flattened layout **plus** `attendees` (user-generated data ⇒ READ in effect).
3. **Decisive identity probe:** the captured `e.calendar.id` value was resolved by the Calendar API itself — `getCalendarById(value)` → **null**, `getEventById(value)` → **the opened EVENT** (returned its title). ⇒ **`e.calendar.id` IS the EVENT id** (26-char event-id format). An earlier reading of it as a calendar id was an assumption, now corrected.

**Final extraction contract** (single function `_extractEventIdentity`, unambiguous, first hit wins):
- (a) documented nested layout `e.calendarEventObject.calendar.{id, calendarId}`
- (b) legacy layout `e.selectedEvent` (inherited PoC evidence shape)
- (c) **observed runtime layout** top-level `e.calendar` (used only when no `selectedEvent`) — `calendar.id` = EVENT id, `calendar.calendarId` = parent calendar
- (d) deprecated top-level `e.id` / `e.calendarId`

M0 reads **only the two stable ids**; `attendees`/`organizer` are never read (PII discipline — test-asserted: attendee data never rendered). No event title/time in the UI (not in the documented field table at any level; the operator sees the event in the Calendar UI).
